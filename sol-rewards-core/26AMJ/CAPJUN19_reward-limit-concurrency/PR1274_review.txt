REVIEW 1: CORRECTNESS & CONCURRENCY FIX
=========================================================

DOES IT FIX THE BUG?
---------------------
Partially. The REWARD-level FIXED window race is correctly solved.
Org-level constraints are not protected — the original race survives for them.


APPROACH SUMMARY
-----------------
The PR introduces a two-phase reservation in RewardConstraintFacade.reserveSlots():

  Hot path  — atomic UPDATE ... WHERE (CONSUMED + delta) <= limit LIMIT 1.
              MySQL row-level lock makes this safe under concurrency when a row exists.

  Cold path — acquires a Redis lock scoped to
              rewardConstraintLock:{orgId}:{rewardId}:{level}:{kpi}:{date},
              does SELECT SUM, calls ensureSummaryRow if needed, then retries the
              UPDATE inside the lock. On failure, releaseOnFailure DECRBYs the
              consumed value back.

This correctly eliminates the duplicate-row INSERT race and the limit breach
for REWARD-level FIXED constraints.


CRITICAL ISSUES (Must Fix Before Merge)
-----------------------------------------

1. Org-level constraints are not protected — Bug A recurs for org-scope

   validateForOrgLevelConstraints() adds org-level constraints to
   wrapper.getValidRewardConstraintList() but reserveSlots() is only called at
   the end of validateForNonOrgLevelConstraints(). Org-level LevelService
   implementations return isPreReserved() = false, so the entire reservation
   path is skipped for org-level constraints.

   Two customers simultaneously hitting an org-level FIXED daily constraint still
   race — both pass the soft evaluation and hit the legacy buildUniqueSummaries /
   blind SET CONSUMED = :value path. The fix must extend reserveSlots() to cover
   org-level constraints too.

2. ensureSummaryRow omits LAST_UPDATED_ON — breaks ETL silently

   The new INSERT in RewardIssueSummaryJdbcRepository.ensureSummaryRow() does not
   include LAST_UPDATED_ON. infra.md guardrail is explicit:
   "Every rewards_utf8_db table write — lastUpdatedOn must be populated —
   ETL delta loads depend on it."

   All 4 new UPDATE methods (incrementConsumedRewardLevelForDate,
   reserveConsumedRewardLevel*, releaseSlot*) also omit LAST_UPDATED_ON = NOW().
   This will silently break Databricks delta loads on all prod clusters.

3. REDIS_LOCK_TTL env var absent from sol-rewards-core-a.json

   The cold-path Redis lock uses redisLockRegistry backed by redis.lock.ttl
   (default 5s). This env var is not added to sol-rewards-core-a.json, so all
   prod clusters use the 5s default. On a slow DB the cold-path ensureSummaryRow
   + UPDATE could exceed 5s and allow a second thread in. The value needs to be
   explicitly set and documented in sol-rewards-core-a.json.


NON-CRITICAL ISSUES (Should Fix)
----------------------------------

4. Unsized new HashMap<>() in all 13 new JDBC methods.
   code.md requires pre-sized collections. Use new HashMap<>(8) for maps with
   up to 6 entries.

5. computeDelta duplicated byte-for-byte in LevelService and
   CustomerLevelReservationHelper. Violates DRY — if POINTS KPI calculation
   changes in one place the other diverges silently.

6. Redundant inner Redis lock for CUSTOMER-level constraints.
   The outer @CustomerLockable already serializes per-customer. The inner lock in
   CustomerLevelReservationHelper for CUSTOMER-level is redundant overhead.

7. RedisCacheKeys constant rewardConstraintLock: is unquoted.
   Every other key in that file is SpEL-quoted. Add a comment explaining it is a
   lock prefix, not a cache name.

CORRECTNESS VERDICT: REQUEST CHANGES
--------------------------------------
The REWARD-level fix is correct and the hot-path atomic UPDATE approach is solid.
Three critical issues must be resolved before merge:
  - Org-level constraints must be included in the reservation path
  - LAST_UPDATED_ON must be added to every new DB write
  - Lock TTL must be explicitly configured in sol-rewards-core-a.json
Once those are fixed and an org-level concurrency test is added, this is mergeable.

CLASS DESIGN ISSUES
--------------------

1. RewardLevelService — two responsibilities

   Pre-PR: pure read-side LevelService (KPI loading, summary building, evaluation).
   Post-PR: also owns the full reservation/release protocol — Redis lock acquisition,
   cycle-sum query, ensureSummaryRow, computeCycleEnd (~140 new lines added).

   The project explicitly created CustomerLevelReservationHelper to isolate
   customer-level reservation away from *LevelService classes. That extraction was
   not applied here. A RewardLevelReservationHelper mirroring
   CustomerLevelReservationHelper would restore cohesion and complete the pattern.

2. RewardIssueSummaryJdbcRepository — nearly tripled in size

   Pre-PR: ~182 lines. Post-PR: ~495 lines. The new methods split cleanly into two
   symmetric groups: reward-level (no userId) and customer-level (with userId).
   Separate RewardLevelSummaryJdbcRepository and CustomerLevelSummaryJdbcRepository
   would match the SRP enforced on the service layer and prevent the file from
   becoming unmanageable when a third constraint level is added.

CLEAN CODE VERDICT: REQUEST CHANGES
--------------------------------------
The dominant structural gap is that the helper-extraction pattern was applied to
customer-level constraints but not to reward-level constraints. RewardLevelService
now carries both read-side and reservation responsibilities, breaking the symmetry
the codebase was building toward. The computeDelta duplication and the
hasSiblingWindowed four-copy duplication are both in newly added code — any future
rule change requires four simultaneous edits. Naming regressions (user_id snake_case,
svc, jdbcRepo) are individually small but collectively inconsistent with surrounding
conventions.

Request changes on:
  1. Extract RewardLevelReservationHelper (mirrors CustomerLevelReservationHelper)
  2. Consolidate computeDelta and hasSiblingWindowed to RewardConstraintHelper
  3. Fix naming regressions (user_id, svc, jdbcRepo, getBinding* -> filterBinding*)
  4. Remove label-style comments; add WHY comments on LIMIT 1 guard and lock key design
  5. Replace ":REWARD:" string literal with rc.getConstraintLevel().name()
