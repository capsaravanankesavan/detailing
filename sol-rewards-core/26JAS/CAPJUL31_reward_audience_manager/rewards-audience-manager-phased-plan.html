Gating Rewards by Audience Membership — the 2-Phase Plan

How Rewards will link to Audience Manager to show a reward only to eligible users — why a naive “one reward, many groups” model breaks, why the fix belongs in Audience Manager, and the phased path to get there.

STATUS: DESIGN EXPLORATION — SEEKING ALIGNMENT · Discussed with: AM Architect · Product · Team Lead

The Business Problem

Brands want to target rewards by audience — today there’s no way to do it

What Product asked for

A brand admin should be able to link a Reward to one or more Audience Groups (e.g. “Gold tier customers”), so that in the Catalogue, the reward is shown only to users who belong to one of those groups.

Why it’s not simple

Audience Group membership isn’t instant — a group has to be “materialized” (built and activated) in Audience Manager before it can even be checked. Getting the linking, timing, and edit behavior right — without ever showing a half-configured or inconsistent reward — is the hard part.

Existing Building Blocks · Where We Start

What Rewards and Audience Manager already have, independently

Reward arrives → needs eligibility → no audience concept exists → Audience Manager owns groups → group has a lifecycle → not connected today

Reward (Rewards system) A brand-configured incentive shown in Catalogue. Today: zero concept of audience-based visibility.

Audience Group (Audience Manager) A brand-defined segment, backed by a filter rule evaluated live via an external rule engine (RBS). Lifecycle: created → lookup enabled → materializing → READY (or ERROR). Membership checks only work once READY.

The gap: nothing today lets a Reward say “only show me to users in Audience Group G.” Everything that follows is about closing that gap correctly.

Reference · Product’s Two Hard Requirements

The rules any design must satisfy, no exceptions

# Requirement Plain English
R1 Hassle-free launch A reward should launch only when all its linked audience groups are READY — never half-configured
R2 No mixed state on edit Editing a reward’s group list (e.g. [AG1,AG2,AG3] → [AG1,AG4,AG5]) must never serve a mixed combination mid-transition — it’s the complete old set, or the complete new set. Never [AG1,AG4] alone

These two rules — not engineering preference — are what eliminated our first design and drove us to the final model. Everything on the next few slides traces back to satisfying R1 and R2.

The First Design We Tried

Reward (1) —— (*) Audience Group — the obvious model

Reward created → admin picks N groups → save a flat list → that’s it?

It looks obviously right: a reward can need more than one group, so make it a list. This is where the trouble starts.

Where It Breaks · CREATE (R1)

Audience Manager has no concept of “jointly ready”

What we need

Don’t launch the reward until every linked group reports READY.

What AM actually gives us

AM tracks readiness strictly per group, independently — there is no primitive anywhere for “this set of groups is jointly ready.” Rewards would have to invent and track that joint-readiness fact itself, watching whichever group finishes materializing last.

Not a blocker by itself — this alone could be solved with a background watcher. The real break is on the next slide.

Where It Breaks · EDIT (R2) — the harder one

A flat, mutable list cannot represent “old” and “new” at the same time

Old list serving [AG1,AG2,AG3] → admin edits to [AG1,AG4,AG5] → mutate in place? → a concurrent Catalogue read can see a half-updated list → exactly the forbidden mixed state

The root cause

You need two full generations of the group-list to coexist — one still live, one materializing in the background — until the new one is completely ready, then swap atomically. A flat, single list has no place to put a second generation.

We were conflating two different kinds of state that need separate homes: (1) per-group status — AM already gives us this — and (2) per-edit “is this whole new set ready as a unit” — AM gives us nothing for this, and a flat list has nowhere to keep it.

The Entity We Designed To Fix It

A versioned wrapper — never mutate the live list, always mint a new one

RewardAudiences  (one row = one "generation" of a group-list)
  ├─ status: PENDING_ACTIVATION | ACTIVE | ARCHIVED
  └─ (*) AudienceGroup   [the set, for this generation]

Edit reward → mint NEW generation (PENDING_ACTIVATION) → old generation keeps serving, untouched → new generation’s groups materialize in background → all READY? → atomic swap → old generation archived

The key trick: subscribe to Audience Manager using entityId = reward_audiences.id, not rewardId — so the old generation’s AM subscriptions and the new generation’s AM subscriptions are two completely independent, non-interfering lineages. This is what makes “old keeps serving while new materializes” actually work.

This correctly solves R1 and R2. But it raised a bigger question — is this really a Rewards-domain concept?

The Question We Took To The AM Architect

“Is a live, evaluatable set of groups really Rewards-domain logic?”

We checked three existing Audience Manager concepts, to see if “a set of groups treated as one unit” could reuse something that already exists, rather than inventing it fresh inside Rewards.

Reference · What We Checked In Audience Manager

Three existing AM concepts, and whether they fit

AM Concept Does it fit our need?
Parent/Child Audience hierarchy No — single parent per child, rigid AND-composition tree, built for nested refinement — not an admin-chosen arbitrary set
MERGE (Union / Intersect) Partial — AM can compute “A OR B,” but only as a static, materialized snapshot (a batch file merge) — not a live filter a real-time lookup can resolve
Multiple rules per group No — one Audience Group = exactly one rule, always. Multiple rules = multiple groups

None of the three is a fit as-is. But the pattern across all three is telling: every primitive this idea would need — group definitions, rule evaluation, live materialization, RBS integration — already lives inside Audience Manager, just not assembled into a “live set” concept yet.

Outcome With The AM Architect

Joint conclusion: this belongs in Audience Manager, not Rewards

“A set of groups, evaluated live, potentially with OR logic, is fundamentally an Audience Manager domain concept — it belongs next to Audience Group and the hierarchy, not reinvented inside Rewards.”

Why AM, not Rewards

  • AM already owns every primitive this needs — group definitions, rule evaluation, live materialization, RBS integration
  • Rewards would otherwise duplicate group-set semantics that conceptually belong where groups themselves live
  • Other future consumers beyond Rewards will want “match any of these groups” too — solving it once in AM benefits the whole platform
  • AM is the only place that could ever deliver true live OR/union — Rewards building its own set-tracking can never get past AM’s materialized-snapshot limitation

This new AM entity doesn’t exist today. We’re calling it AudienceGroupSet — a forward-looking AM roadmap ask, not something to block our launch on.

Our Answer · A 2-Phase Plan

Ship now on what exists. Extend once AM builds the set entity.

Phase 1 (now) Reward (1)—(1) Audience Group → ships on AM as-is today

Phase 2 (future) Reward (1)—(1) Audience Group Set → once AM builds AudienceGroupSet

Why strict 1-to-1 first is not a compromise

Only one group ⇒ no combination to ever be “mixed” ⇒ R2 is eliminated by design, not engineered around. Readiness check happens before linking is allowed ⇒ R1 is satisfied by construction — no background cutover machinery needed at all.

Phase 1 · Data Model

Reward (1) —— (1) Audience Group

Reward
 ├─ audience_group_id            (single FK, nullable)
 ├─ audience_group_last_status   (cached: READY | PROCESSING | ERROR)
 └─ audience_group_last_checked_at

Deliberately the simplest possible shape — a single nullable pointer plus a cached status for display. No versioning, no generations, no background cutover job needed, because there is never more than one group to coordinate.

What this needs from AM: nothing new. Phase 1 uses Audience Manager’s existing subscribe() and status-check APIs exactly as they are today.

Phase 1 · Brand Admin Experience — CREATE

Finish setup in AM first, then link in Rewards

Admin sets up Audience Group in AM UI → waits for READY → opens Rewards UI → picks that group to link → Rewards blocks the link unless it’s already READY → link succeeds → reward is immediately eligible, no waiting

If the group isn’t ready yet, Rewards UI shows a clear message: “Finish setting this up in Audience Manager first.” No polling, no pending state inside Rewards — readiness is guaranteed the moment linking is allowed to succeed.

Phase 1 · Brand Admin Experience — EDIT

A single atomic pointer swap — no transition window at all

Admin picks a different, already-READY group → same gate applies → reward keeps serving the old group, completely unchanged, until the swap fires → swap is one atomic field update, not a multi-step transition → old group unsubscribed only if no other reward still uses it

Because there is only ever one group, R2’s “never serve a mix” requirement isn’t something we engineer around with versioning — there is structurally nothing to mix. The edit either hasn’t happened yet (old group, fully valid) or has happened (new group, fully valid).

Phase 2 · Data Model

Same shape, new target — Reward (1) —— (1) Audience Group Set

Reward
 ├─ audience_group_set_id           (single FK — now points at a SET)
 ├─ audience_group_set_last_status
 └─ audience_group_set_last_checked_at

Rewards’ own model barely changes from Phase 1 — the complexity of “many groups, joint readiness, OR logic” stays entirely inside AM’s new entity. This is exactly why Phase 1’s shape matters: it’s forward-compatible with almost no rework on the Rewards side.

Phase 2 · Brand Admin Experience

True OR-across-groups eligibility, once AM builds the set entity

Admin builds a set of groups in AM UI (e.g. “Gold tier OR Platinum tier”) → AM materializes + tracks joint readiness for the whole set → admin opens Rewards UI, picks that set → same pre-link readiness gate, now checking the whole set → reward supports true OR-across-groups eligibility, live

Edit flow is identical in shape to Phase 1 — swap the audience_group_set_id pointer only when the new target set is ready. AM’s set entity internally handles multi-group materialization and versioning — Rewards doesn’t reinvent generation-tracking, because AM does it once for every consumer.

What Phase 2 Needs From Audience Manager

The roadmap ask, made concrete

Ask Detail
New entity: AudienceGroupSet A brand-defined collection of groups, with joint readiness tracking and — ideally — live OR/union evaluation, not just a materialized snapshot
UI support Brand admins need an AM-side UI to create/manage a set: add/remove member groups, see per-group and overall set status
APIs subscribe / status / lookup equivalents scoped to a set, mirroring today’s per-group APIs — so Rewards’ integration pattern carries over unchanged
