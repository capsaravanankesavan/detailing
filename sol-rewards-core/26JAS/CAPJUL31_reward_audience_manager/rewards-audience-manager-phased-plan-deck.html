The Business Problem

Brands want rewards targeted by
audience — today there’s no way to do it

What Product asked for

Let a brand admin link a Reward to one or more Audience Groups in Audience Manager (AM), so the reward shows in Catalogue only to users belonging to one of those groups.

Why it’s not simple

An Audience Group isn’t instantly usable — it must materialize in AM (async, via an external rule engine) before membership can even be checked. Getting linking, timing, and edit behavior right — without ever showing a half-configured reward — is the hard part.

Reference · The Rules That Drive Everything

Product’s two hard requirements

# Requirement Plain English
R1 Hassle-free launch A reward should launch only when all its linked audience groups are READY — never half-configured.
R2 No mixed state on edit Editing a reward’s group list (e.g. [AG1,AG2,AG3] → [AG1,AG4,AG5]) must never serve a mixed combination mid-transition. It’s the complete old set, or the complete new set — never [AG1,AG4] alone.
These two rules — not engineering preference — are what broke our first design and drove the entire journey that follows.

It looks obviously right: a reward can need more than one group, so make it a list. This is exactly where the trouble starts — on both create and edit.
Where It Breaks · CREATE (R1)

AM has no concept of
“jointly ready”

What we need

Don’t launch the reward until every linked group reports READY, together.

What AM actually gives us

AM tracks readiness strictly per group, independently. There is no primitive for “this set of groups is jointly ready” — verified: the lookup-mapping model has no cross-group relationship at all.

Rewards would have to build and maintain that composite “all-ready” state itself — watching whichever group finishes materializing last. Not fatal alone — the real break is on edit, next.
Where It Breaks · EDIT (R2) — the harder one

Option Why it fails
  1. Mutate list in place
Remove AG2/AG3, add AG4/AG5 directly — but AG4/AG5 aren’t READY yet. A concurrent Catalogue read during this window sees a half-updated list: exactly the forbidden mixed state.
  1. Stage new list, cut over later
Needs the reward to hold two full versions of its group-list at once — one live, one materializing. A flat list column has no place to put a second generation.
State-Management Problem, Restated

Two lifecycles, conflated into one field

Lifecycle Who tracks it today
  1. Per-group materialization state
    (PROCESSING / ACTIVE / ERROR)
AM gives us this — fine, per group.
  1. Per-edit “generation” composite state
    (is this WHOLE set, as a unit, ready to go live)
Nothing gives us this — must be modeled entirely in Rewards, and a flat mutable list has no place to hold “the pending generation” separately from “the live generation.”
Without solving row 2, R2 cannot be honored. This is what pushed us to invent a new structural entity.
The Entity We Designed To Fix It

reward_audiences: a versioned wrapper
— never mutate, always mint a new generation

reward_audiences ( id, reward_id, status, – PENDING_ACTIVATION | ACTIVE | ARCHIVED created_at, activated_at ) reward_audience_group ( reward_audiences_id, audience_group_id, last_known_status )
edit rewardmint NEW generation
→
old generationkeeps serving, untouched
→
new generationmaterializes in background
→
all ACTIVE?atomic swap

The key trick

Subscribe to AM using entityId = reward_audiences.id, not rewardId — so the old and new generations’ AM subscriptions are two completely independent lineages. This is what makes “old keeps serving while new materializes” actually work. It correctly solves R1 and R2.

Reference · Remaining Open Edge Cases In This Model

Even with reward_audiences, four things
still needed an explicit answer

Edge case What’s still open
Concurrent edit mid-flight Does a second edit block, or abandon (unsubscribe) the first pending generation?
Cancel / rollback of a pending edit Same abandon-and-unsubscribe path — needs an explicit trigger.
Permanently-stuck group A group that never reaches ACTIVE (a Databricks-class permanent failure) silently stalls the edit forever unless surfaced via alerting.
Archive-unsubscribe ordering Must happen strictly after confirmed cutover — never before or concurrently.
This model technically works. But before finalizing it, we asked a more fundamental question — is a “set of groups treated as one unit” really Rewards-domain logic at all?
Discussion With The AM Architect

Three existing AM concepts we checked
— and whether they fit

AM Concept Does it fit our need?
Parent / Child Audience hierarchy No — single parent per child (verified: parentGroupId is one field, not a list), rigid validated AND-composition tree, event-driven sync (not even a daily cron) — built for nested refinement, not an admin-chosen arbitrary set.
MERGE (Union / Intersect) Partial — AM can compute “A OR B,” but only as a static, materialized user-list snapshot — not a live filter a real-time lookup can resolve. MERGE groups are explicitly excluded from the hierarchy too.
Multiple rules per group No — verified: one Audience Group = exactly one rule (AudienceGroup.uuid is a single field). Multiple rules are always modeled as multiple groups.
None of the three is a fit as-is. But every primitive this idea needs — group definitions, rule evaluation, live materialization, RBS integration — already lives inside Audience Manager, just not assembled into a “live set” concept yet.
Outcome With The AM Architect

Joint conclusion: this belongs in
Audience Manager, not Rewards

“A set of groups, evaluated live, potentially with OR logic, is fundamentally an Audience Manager domain concept — it belongs next to Audience Group and the hierarchy, not reinvented inside Rewards.”

1

AM already owns every primitive this needs — group definitions, rule evaluation, live materialization, RBS integration.

2

Rewards would otherwise duplicate group-set semantics that conceptually belong where groups themselves already live.

3

A background poll/cron is still needed either way — AM has no push mechanism today. Moving the entity into AM relocates where the set’s membership rules live, it doesn’t remove the polling concern.

4

Only AM could ever deliver true live OR/union — Rewards can never get past AM’s materialized-snapshot limitation on its own.

Working name on the AM side: AudienceGroupSet. Future AM roadmap work — not something to block this design on.
Our Answer

A 2-phase plan

Phase 1 (now)

Reward (1) —— (1) Audience Group

Ships on AM’s APIs as they exist today. No AM changes needed.

Phase 2 (future)

Reward (1) —— (1) Audience Group Set

Once AM builds the new AudienceGroupSet entity.

Why strict 1-to-1 first is not a compromise

Only one group ⇒ no combination to ever be “mixed” ⇒ R2 is structurally eliminated. Readiness check moves to before linking is allowed ⇒ R1 is satisfied by construction — no background cutover machinery needed on the Rewards side at all.

Phase 1 · Data Model & Brand Admin Experience

Reward (1) —— (1) Audience Group

reward ( id, audience_group_id, – single FK, nullable if unlinked audience_group_linked_at, audience_group_last_status, – READY | PROCESSING | ERROR | unknown (cached) audience_group_last_checked_at, audience_group_alert_raised_at – suppresses duplicate tickets )

CREATE

Admin sets up group in AM UI, waits for READY
Opens Rewards UI, picks that group
Rewards blocks the link unless already READY
Link succeeds → immediately eligible, no waiting

EDIT

Admin picks a different, already-READY group
Same pre-link gate applies
Reward keeps serving the old group until swap
Swap = one atomic field update, then unsubscribe old (if unreferenced)
What this needs from AM: nothing new — uses today’s existing subscribe() and status-check APIs as-is.
Phase 2 · Data Model & Brand Admin Experience

Reward (1) —— (1) Audience Group Set

reward ( id, audience_group_set_id, – single FK – now points at a SET audience_group_set_last_status, audience_group_set_last_checked_at )

Brand admin experience

Admin builds a set of groups in AM UI (e.g. “Gold tier OR Platinum tier”). AM materializes + tracks joint readiness for the whole set. Same pre-link readiness gate as Phase 1, now checking the whole set — true OR-across-groups eligibility, live.

Why Rewards barely changes

Edit flow is identical in shape to Phase 1 — swap the audience_group_set_id pointer only when the new target set is ready. AM’s set entity owns multi-group materialization and versioning — Rewards doesn’t reinvent generation-tracking.

What Phase 2 Needs From Audience Manager

The roadmap ask, made concrete

Ask Detail
New entity: AudienceGroupSet A brand-defined collection of groups, with joint readiness tracking and — ideally — live OR/union evaluation, not just a materialized snapshot.
UI support Brand admins need an AM-side UI to create/manage a set: add/remove member groups, see per-group and overall set status.
APIs subscribe / status / lookup equivalents scoped to a set, mirroring today’s per-group APIs — so Rewards’ integration pattern carries over unchanged.
